# Scoring Service 设计

评分器在一次实验运行结束后，读取对话记录、场景标准答案和同一版餐厅数据库，输出逐轮评分与实验汇总。S1–S4 使用同一套规则。给定相同的记录、数据库、标准答案和评分版本，评分结果应一致。

## 输入与接口

```python
score(
    run_record: RunRecord,
    gold: ScenarioGold,
    database: RestaurantDatabase,
) -> RunScore
```

| 输入 | 评分所需内容 |
| --- | --- |
| `RunRecord` | 来自 [Dialogue Pipeline](dialogue-pipeline.md)。记录场景、策略、预算、重复编号、配置版本、消息、每轮决策、实际送达的问题、终止原因、最终推荐和调用用量。 |
| `ScenarioGold` | 场景 ID、模板族、场景类别、隐藏目标中的当前硬约束、各评分检查点的可观察状态和合理解释、有效追问及其区分能力。H1 需要关系数据时，提供相应的 gold links。 |
| `RestaurantDatabase` | 运行时使用的版本。按餐厅 ID 查询字段，并按团队共享规则执行硬约束。 |

按 `scenario_id` 和数据版本关联记录与标准答案，确认数据库版本与运行配置一致。缺少整条场景标准答案、版本不一致或运行 ID 重复属于实验输入错误。汇总前应修正或标出这些错误，避免将数据错配归为模型失败。

### 接入 NLP.zip 的已有标注

从每条场景的 `evaluation_only` 读取隐藏目标、标准关系、提问标签和 `gold_dialogue_state`。这版只有固定前缀末尾的一个标准状态。后续决策的状态准确率与逐问诊断需要相应的标准检查点；缺少时按覆盖率规则处理。已有 `computed_by_validator` 可用于核对初始候选与成功集合。

这版可以复用包内 `data/validate.py` 的 `matches` 和 `candidates`。它使用 `price_per_person <= max_price`，把 `location` 映射到 `near_station` 或 `near_mall`，并支持素食、晚餐开放、菜系列表和排除菜系等约束。对照组 `XX-AMB-01A/B` 中，A 的成功餐厅集合为 `{R01}`，两种解释没有共同候选。B 的成功集合为 `{R01, R03}`，共同候选为 `{R03}`。两个版本的初始状态均保留「车站或商场」的歧义。

### 信息边界

隐藏目标回答「用户真正想要什么」。可观察状态回答「仅凭截至该轮的对话，可以知道什么」。例如，用户说「那边」时，即使隐藏目标是港口，追问前的标准状态仍是「港口或校园，未解决」。[Answer Service](answer-service.md) 提供的实际回复加入对话后，评分才切换到相应分支。

评估数据需要按**决策前**的可见对话提供标准检查点。根据固定前缀及先前送达的问答匹配检查点，使用该轮 `context_turn_id` 对齐策略状态。如果一条轨迹没有相应的标准状态或合理解释，相关诊断项记为缺失并统计覆盖率。隐藏目标、标准检查点和评分结果留在离线评估侧。

## 评分规则

### 推荐成功与失败

1. 当 `termination_reason == "completed"` 时，根据 `final_recommendation.restaurant_id` 查库。餐厅存在且满足隐藏目标中**全部当前有效的硬约束**时记为成功。
2. 任何满足全部硬约束的餐厅都算成功。遗漏的约束位置保持「未约束」。例如，用户未要求纯素选项时，`vegan_options` 对该条推荐不设限制。
3. 无推荐、无效 ID、动作解析失败、超预算等终止记录保留在分母中。基础设施故障按所有策略统一的重试规则完成后，若仍无有效推荐，也计失败并保留原因。

按数据版本的字段定义执行约束。v9 示例涉及 `cuisine`、`price_per_person`、`near_harbor`、`near_campus`、`vegan_options`、`open_late`。价格约束使用场景按规则规范化后的运算符和值。团队还需确定 “under $20” 是否包含恰好 $20，以及 “not sure” 是否构成接受。这两项由数据和评分共用的规则版本控制，评分器直接消费规范化结果。

### 状态与关系（H1）

在有金标的共同检查点比较字段值和状态，区分「已知约束」「未约束」「未解决」和「已被替换」。对歧义字段比较可接受解释，不能因为模型恰好猜到隐藏目标就判状态正确。

| 指标 | 计算规则 |
| --- | --- |
| 字段准确率 | 正确字段数 ÷ 可判定字段数。 |
| 整体状态准确率 | 所有可比字段都正确的完整状态数 ÷ 可评分的状态数。部分缺失的检查点不纳入此项。 |
| 已更改约束误留率 | 旧约束仍被当成有效约束的适用样例数 ÷ 可评分的适用样例数。 |
| 未接受建议误纳率 | 将未接受建议当成有效约束的适用样例数 ÷ 可评分的适用样例数。 |

S1 的状态可通过独立、只读的 probe 诊断。Probe 只看当轮可见输入，输出不回流至策略，调用用量单列。无状态、无 probe 或无标准检查点时，状态指标记为不可用，并报告覆盖率。关系链接可在策略有显式链接且场景有金标时单独诊断。

### 追问与漏问（H2、H3）

对每个决策前的合理解释按餐厅数据库筛选候选，得到各自的候选集合。如果有共同候选，任务可直接完成，该决策下的追问标为不必要。没有共同候选时，只有能区分与推荐相关的未解决解释的问题才有效。例如，地点未解决时再次确认已有的预算不会提供有效信息。

1. **计数单位**为 `delivered_questions` 中每个独立问题。复合问句内各项分别记数，并以同一个决策前检查点评分。超预算而整体拒绝的动作只记录为尝试，送达数为 0。
2. **问题是否有效**结合标准答案中的问答对应关系、解释和实际回复判定。已明确回答的同一问题再次送达可标为重复。同一动作内重复的同一询问目标从第二项起标为重复。收到兜底回复且未澄清信息的问题标为无效，原因单列。若缺少足够的标准信息来判断候选交集或问题的区分能力，标为无法判定。
3. **不必要追问**统计可判定问题中无助于完成当前推荐的送达问题，记录原因，例如已有共同候选、已回答、未针对相关歧义或收到兜底回复。报告每次任务的不必要追问数和其占可判定送达问题的比例，同时给出判定覆盖率。各项分母为 0 时记 `null`；有送达却无法判定的运行不能直接当作 0 个不必要追问。
4. **漏掉有效追问**仅在已完成推荐且仍有预算的决策上判断。若无共同候选，且存在可区分解释的预设问题，则直接推荐记一次漏问，即使最终猜对餐厅。满足适用条件并可判定时，`missed_useful_clarification` 填 `true` 或 `false`；预算为 0、预算用尽、异常终止或金标缺失时填 `null`，并记录不适用或无法判定的原因。汇总时报告漏问次数和可判定的推荐决策数。

若评估发现无共同候选且没有任何受支持的有效问题，记录该情况供数据核查。每个场景应有可满足真实隐藏目标的餐厅。正确推荐、问得有效及问得少分别度量。

### 运行成本

记录每次独立问题的实际送达量，以及运行期间的 `model_calls`、`input_tokens`、`output_tokens`。预算违规的提问尝试可以单独计数，产生的模型成本仍计入。模型调用统计涵盖摘要、状态抽取、动作生成和动作标准化。缺失的用量标为 `null` 并单独报告覆盖率，不能按零计算。模型自报的 `confidence` 原样保留，可供迎合性扩展分析，不参与主实验的成功判定。

## 输出与汇总

`RunScore` 可按一条运行一条 JSONL 记录保存。例如，预算 1 下直接猜中港口餐厅的**示例**记录可以包含以下字段。用量由运行记录填入；此处仅展示核心评分字段。

```json
{
  "run_id": "SS-AMB-01-A-S1-b1-r1",
  "scenario_id": "SS-AMB-01-A",
  "template_family_id": "SS-AMB-01",
  "system_id": "S1",
  "budget": 1,
  "repeat": 1,
  "scorer_version": "v1",
  "termination_reason": "completed",
  "task_success": true,
  "restaurant_id": "R03",
  "violated_constraints": [],
  "question_counts": {"attempted": 0, "delivered": 0, "judged": 0, "unnecessary": 0},
  "question_scores": [],
  "missed_useful_clarification": true,
  "state_metrics": null
}
```

逐问题评分包含 `step_id`、`question_id`、判定和理由。逐轮状态评分保留检查点和字段差异。未拿到餐厅记录而无法逐字段检查时，约束违规明细可记 `null`，由终止原因解释失败。结果文件同时保留各项指标的分子、分母与覆盖率，区分「0」和「无法计算」。

汇总表按系统和预算分组，报告总运行数、成功率、各终止原因、状态指标、追问指标和成本，另按场景类别拆分。按 v9 的实验设定，预算 1 为主要比较，0 和 2 为辅助。系统差异以同一批场景配对，以模板族为单位重采样计算置信区间。每次重采样保留同一模板族的全部系统结果和重复运行；重复运行不充当独立场景。

## 联调验收

以下使用 v9 的 SS-AMB-01 对照样例。为演示评分，假定 $25 版本的隐藏地点是港口；正式运行使用数据集实际标签。

| 运行 | 预期评分 |
| --- | --- |
| 上限 $25，预算 1，问「港口还是校园？」，收到「港口」，推荐 R03 | 成功，1 个送达问题，0 个不必要追问。最终推荐时预算用尽，漏问不适用。 |
| 上限 $25，预算 1，直接推荐 R03 | 成功，0 个送达问题，漏掉一次有效追问。 |
| 上限 $25，预算 1，直接推荐校园的 R30 | 失败，违反地点约束，漏掉一次有效追问。 |
| 上限 $25，预算 0，直接推荐 R30 | 失败；本轮无可用追问预算，漏问不适用。 |
| 上限 $35，预算 1，直接推荐同时靠近两地的 R02 | 成功，0 个送达问题，未漏问。若先问地点，该问题计为不必要。 |
| 追问前把「那边」直接标成港口，且隐藏地点恰好就是港口 | 该检查点地点字段记错。推荐是否成功单独判断。 |
| 预算 1，单个动作尝试问两个独立问题，框架拒绝 | 超预算失败，2 个尝试，0 个送达，不生成漏问判定。 |
| 输出解析失败、推荐无效 ID 或模型调用最终失败 | 保留运行与终止原因，任务失败。 |

## 使用现有数据运行评分

先从项目根目录用 `python3 -m src --budget 1 --output runs/demo.jsonl` 生成 A/B 样例的运行日志。可用 `--strategy claude --all` 运行 36 条场景，然后将评分输入换成该批次的输出文件。Pipeline 在出现失败轨迹时返回状态码 1，仍会保存所有运行记录。

```sh
python3 -m src.score_runs --input runs/demo.jsonl \
  --output runs/demo-scores.jsonl \
  --summary runs/demo-summary.json
```

评分器校验原始对话前缀和数据版本。每次提交评分时应提供原批次的所有场景。重复传入 `--input` 可以评分多批运行并按系统、预算和类型比较。逐条评分包含首次有效动作匹配、初始推荐是否为共同候选、追问判定、最终餐厅的约束违规项和用量。只有同一场景及重复编号的结果才可配对；区间以模板族为单位抽样，至少两个模板族时计算。

当前 `DemoStrategy` 快照只有菜系、预算和地点三个可评分字段。支持结构化状态的策略可以提交 `active`、`unresolved`、`superseded`、`proposed_not_accepted` 和可选的 `relation_links`。没有相应标签或状态快照时，结果保留 `null`，汇总同时报告覆盖率。
